## 🟩 Supabase database setup

1. Open the selected project's **Connect** panel. Copy its exact host, port and username. Percent-encode reserved characters in the password. For Vercel runtime connections use the transaction pooler; for migrations use direct connectivity, or the session pooler when the job has only IPv4. Do not run schema migrations through transaction pooling. [Connection guidance](https://supabase.com/docs/guides/database/connecting-to-postgres)
2. This project's production preflight requires exactly one `sslmode=verify-full` parameter; a format pass does not prove a TLS handshake. Supabase signs its Postgres endpoints with its own root CA, which Node's bundled trust store does not include. `prisma migrate deploy` completes its own handshake, but the runtime `pg` adapter used by the application and seeds fails with `self-signed certificate in certificate chain` unless that CA is trusted. `src/lib/db/connection.ts` therefore embeds the published Supabase Root 2021 CA (`src/lib/db/supabase-ca.ts`, SHA-256 `80:70:25:AD:…:E6:CA:FA`) and, only for `*.supabase.com`/`*.supabase.co` hosts with `verify-full`, passes it to `pg` alongside Node's default roots with full certificate and hostname verification. No `NODE_EXTRA_CA_CERTS` setting is needed on Vercel. Never resolve certificate errors by setting `NODE_TLS_REJECT_UNAUTHORIZED=0`, disabling SSL, or disabling certificate validation. If Supabase rotates its root, replace the embedded certificate from the dashboard's **Connect → SSL certificate** download and update the fingerprint test.
3. Check the database identity and existing migration history before writing. Back up existing valuable data. Inspect every pending SQL migration in `prisma/migrations`; Phase 16 adds none. Do not use `db push`, migration reset or a destructive re-seed to repair drift.
4. Keep the `app` schema out of Supabase's exposed Data API schemas. Existing migrations enable table RLS and revoke browser-role access. Prisma's trusted server connection relies on application authorization and can bypass those policies as the schema owner. Preserve owner checks in every loader and action; do not grant `anon` or `authenticated` access to make a server query work.
5. Configure the migration job's private values, then run the commands below from the verified release checkout. `DIRECT_URL` takes precedence for migrations and seeds; runtime code uses `DATABASE_URL`.

```bash
npm ci
npm run deploy:check -- --migrations
npm run db:validate
npm run db:deploy
npm run seed:validate
npm run db:seed
```

Prisma stores `_prisma_migrations` in the schema named by the URL's `schema` parameter, defaulting to `public`. The production database was migrated with no `schema` parameter, so its history lives in `public._prisma_migrations`; keep future `DIRECT_URL` values in that same form, because a URL with `schema=app` would make Prisma look for `app._prisma_migrations` and attempt to reapply everything.

Seeding writes the repository's curated content and roadmap definitions. Review existing-content conflicts before running it. Seeding runs in two phases, problems first and then roadmaps, and is not atomic across them. If an administrator has edited an already-seeded problem (the edit clears its seed hash), the problem phase detects the conflict before writing any problem and stops the command, so roadmaps are not attempted (a conflict that only appears concurrently, during the batch writes, can leave earlier problem batches committed). If a seeded roadmap was edited, the roadmap phase rolls back all roadmaps (its writes are one transaction) but any new problems from the same run are already committed. Either way, new content cannot be fully added until the edited content is reconciled with the seed files. Generated problem fixtures remain a separate reviewed draft workflow; do not publish them as part of deployment. Run seeds once in a trusted job, never on every Vercel build. Confirm migration history, published library data and roadmap reads afterward.

The current adapter allows up to five connections per application instance. Monitor aggregate connection usage under actual concurrency and tune against the project's available pool budget before increasing traffic. Verify transaction-pool compatibility against the installed adapter during live smoke testing; local PostgreSQL CI cannot prove provider pooling behavior.

The placeholder must be replaced with the actual intended user's UUID. Registration never grants admin privileges. Authorization reads the application role, not user-editable metadata. Confirm a normal account cannot open or invoke admin features.

### Use one hostname for sign-in and password reset

Auth cookies, including the one-time PKCE code verifier that a confirmation or password-reset link needs, belong to a single hostname. Every email link returns to `${APP_URL}/auth/callback`, so a sign-in, signup or reset that **starts on any other hostname** can never finish: the callback finds no verifier, fails without any visible error, and the single-use link has already been spent. Vercel serves the same deployment on several hostnames: the production domain, a team-scoped alias (`<project>-<team>.vercel.app`, which on 2026-10-12 sat behind Vercel Authentication and redirected every path to `vercel.com/sso-api`), per-deployment URLs and branch URLs. Browser-saved passwords are also stored per hostname, so a password saved on one host will not autofill on another.

- **Use the canonical origin** (`APP_URL`, currently https://algosprint-brown.vercel.app) for every account flow.
- **Safeguard in the app:** in a production deployment (`VERCEL_ENV=production`), `src/proxy.ts` redirects GET and HEAD requests for `/login`, `/register`, `/forgot-password`, `/reset-password` and `/resend-confirmation` from any other hostname to the same path on `APP_URL`, using a temporary uncached redirect. The target always comes from `APP_URL`, never from the request. Preview deployments and all other pages are unaffected, and an unset or malformed `APP_URL` disables the redirect. `src/lib/supabase/canonical-host.ts` holds the rule and `tests/canonical-host.test.ts` covers it.
- **Supabase side:** the **Site URL** and the allowed redirect URL must be the canonical origin and its exact `/auth/callback`, as described above. If `redirectTo` is not on the allow-list, Supabase redirects to the Site URL instead.

## 🟨 Keeping the free project awake

Supabase **pauses a free-plan project after about a week without activity**. While it is paused, `/` and `/login` still render (they need no database) but every database-backed page, `/problems` and `/roadmaps` first, returns HTTP 500, and nobody can sign in. The 2026-10-12 incident below shows exactly that. Data is not lost, but Supabase limits how long a paused project can be restored, so do not leave one paused.

- **Detect it:** `.github/workflows/keep-alive.yml` runs on the odd days of each month, so scheduled runs are at most two days apart (and on demand from the Actions tab). It requests `/`, `/login`, `/problems` and `/roadmaps` on the production site and fails if any is not HTTP 200. A paused project looks like `/problems` and `/roadmaps` failing while `/` and `/login` pass. GitHub can delay or skip scheduled runs. It sends failure notices only to the person who last edited the schedule, and only if their notification settings allow it, so check the Actions tab; do not rely on email.
- **Best-effort activity:** regular reads of those pages query the database. To also make one direct request to Supabase's API, set two repository variables under Settings → Secrets and variables → Actions → Variables: `SUPABASE_URL` (the project URL) and `SUPABASE_PUBLISHABLE_KEY` (the publishable key). Both are public values, not secrets. Supabase does not document exactly which requests reset its inactivity timer, so these requests reduce the risk of a pause but cannot guarantee against one. A red run, or a failing page you notice yourself, is the real signal.
- **Restore it:** open the project in the Supabase dashboard and choose **Restore project** (the Supabase MCP `restore_project` tool does the same). Wait until the status is healthy, then re-run the workflow. Restoring needs no code change, migration or seed.
- **Remove the limit:** the Pro plan does not auto-pause. Set `SITE_URL` as a repository variable if the production domain changes.

### Backup and restore runbook

The [current provider guidance](https://supabase.com/docs/guides/platform/backups) recommends regular off-site exports for free-tier projects; automatic daily backups are documented for paid plans. A healthy database or repeatable content seed is not a backup of account data.

Before treating disaster recovery as accepted:

1. Select an encrypted backup destination, retention policy and acceptable recovery-point/recovery-time objectives. Keep exports, credentials and account data outside Git, CI artifacts and public logs.
2. From a trusted operator environment, verify the exact source project, connection/TLS settings and PostgreSQL tool compatibility. Use the documented provider export workflow; include the application schema, authentication data and migration history, plus any separately managed objects or roles needed for recovery. Database backups do not include Storage object files.
3. Restore into a new isolated test project/database. Confirm the target identity before any restore; never rehearse over the live project. Keep outbound mail and hosted code execution disabled in the target.
4. Compare table counts and stable row fingerprints; verify notes, saved progress, submissions, migrations, constraints, RLS and browser-role grants. Exercise sign-in, ownership, account recovery and the application HTTP smoke flow against the restored environment.
5. Record export time, restore time, actual recovery point and test results. Retain the encrypted off-site copy and repeat the rehearsal after material schema/provider changes.

### Code rollback and monitoring

Before releasing, record the previous Ready production deployment and its exact commit. For an application-only regression, inspect the intended project and use the provider's rollback command against that known compatible deployment, then verify the canonical alias, public pages and affected account flow. A code rollback neither reverses a database migration nor restores deleted data. Review schema compatibility separately; prefer a reviewed forward fix for a database issue. Vercel rollback also changes automatic domain-assignment behavior, so verify how subsequent releases will be promoted before resuming them.

The existing `Production health check` workflow remains the automated public monitor. Check its Actions result and repository notification settings; successful HTTP GETs do not prove email delivery, private ownership or code-runner availability. After a release, query deployment-scoped request and runtime errors with explicit time bounds and exhaust pagination. Record subscription/retention gaps instead of treating missing logs or usage as a clean result. Repeat authenticated admission/capacity checks without deliberately exhausting production quotas.

### Optional Auth IP forwarding

Server-side Auth requests otherwise share the Vercel server IP rate-limit bucket. Leave `SUPABASE_AUTH_IP_FORWARDING` unset unless forwarding is configured. To opt in on Vercel, set it to `true`, provision a server-only `SUPABASE_AUTH_FORWARDING_SECRET_KEY` (`sb_secret_…`), and enable **Authentication → Rate Limits → IP Address Forwarding** in the matching Supabase project. Invalid enabled configuration fails before a provider request. The secret is used only for the current end-user Auth endpoints; Data and Auth admin calls retain the publishable key. User bearer tokens and cookies retain their existing behavior. No production setting is changed by deploying this code.

Before enabling production, verify in a preview with its own Auth project that two controlled browser networks appear with distinct visitor IPs in Auth logs and that refresh and recovery still work. Do not deliberately exhaust production limits. See [Supabase IP forwarding](https://supabase.com/docs/guides/auth/rate-limits#ip-address-forwarding) and [Vercel request headers](https://vercel.com/docs/headers/request-headers#x-vercel-forwarded-for).
