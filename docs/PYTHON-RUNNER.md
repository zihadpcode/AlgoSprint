# Python runner: architecture and the Vercel Sandbox executor

**Status: Python is enabled in production for all 125 published coding problems as of October 21, 2026.** The real signed-in canary passed correct, wrong-answer and runtime-error Run checks, an accepted six-test Submit, saved verdicts and verified progress. JavaScript Run and Submit also passed. [Production verification](evidence/python-production-2026-10-21.md) records the release and database checks.

Python remains off unless all three settings are exactly `CODE_RUNNER_ENABLED=true`, `CODE_RUNNER_PROVIDER=sandbox`, and `PYTHON_RUNNER=vercel-sandbox`. The getter rechecks those settings before returning a shared executor; inspecting capability starts no VM. Removing the Python flag and redeploying disables execution while preserving starters and history.

The complete hosted matrix and five supervisor-specific probes passed against the pinned image and final supervisor/bootstrap: 30 distinct VMs, all confirmed stopped. Evidence is saved below. Earlier failures and held checkpoints are historical evidence, not the current activation mechanism.

### The Python program

The harness reads the JSON argument array from stdin, compiles and `exec`s the learner's code in a fresh namespace (`__name__` is `"solution"`, so `if __name__ == "__main__"` blocks do not run), calls the entry point with positional arguments, redirects the learner's `print()` to stderr, and writes only `json.dumps(result, allow_nan=False)` to the real stdout. `NaN`/`Infinity` therefore become a runtime error. Learner code and the entry point reach Python only as JSON string literals, never by string interpolation into code.

Exit codes are part of the executor contract: `0` success, `3` compile error (`SyntaxError` and friends), `1` runtime error (traceback on stderr), anything else is treated as a runtime error. The application compares stdout JSON itself (`isDeepStrictEqual` on parsed JSON), caps stored stdout at 4,000 characters (stderr keeps its last 4,000, where the exception line is), treats either output stream above 262,144 UTF-8 bytes as a runtime error, and keeps hidden-case inputs, expected values, output and diagnostics out of `SUBMIT` responses and stored results. The harness emits compact Unicode JSON without a newline; see [the shared byte policy](RUNNER-BYTE-LIMITS.md).

### Writing an executor

An executor runs one program against one stdin and reports what happened: `exited` (exit code, stdout, stderr, runtime, memory), `time-limit`, `memory-limit` or `unavailable`. It must give the program no host filesystem, network, environment variables or other processes, and enforce the time and memory budget it is given (already clamped to `RUNNER_LIMITS`). `registerPythonExecutor(executor)` is for controlled tests; production code uses the exact environment settings described above. Runner unit tests use a fake executor. The optional harness test may invoke an already-installed local `python3`; that test is separate from the application runtime.

## Add-on Python starters

`npm run starters:python` regenerates `src/data/seeds/languages/python-starters.json` from `SIGNATURES` (one short stub per slug with `pass`; names and parameters in snake_case). `npm run seed:validate` checks that every slug exists, entry points and parameters are valid non-keyword identifiers, parameters do not collide, and the file matches the generator.

`seedLanguageStarters` in `prisma/seed-language-starters.ts` inserts missing `StarterCode` rows for existing problems. It never updates or deletes, never touches `Problem` rows (so insert-only problem seeding and its content-hash protection are unaffected), is idempotent, and throws a conflict error before writing anything if an existing row for the same problem and language differs. It is deliberately **not** part of `npm run db:seed`: once these rows exist the editor offers Python, but Run and Submit remain disabled unless the managed runner is explicitly enabled. Run `npm run db:seed:python-starters` (`scripts/seed-python-starters.ts`) only after the reviewed runtime is ready for rollout. It reuses the same insert-only, conflict-checked function and is safe to repeat. For a canary, `npm run db:seed:python-starters -- --slug relay-window` (repeatable) seeds only the named problems, so only those offer Python; an unknown slug is an error. Check the seed result for missing problems and read back the selected rows before treating the canary as installed.

## Earlier runtime options (historical)

The owner selected Vercel Sandbox, so the WASI and in-process directions below were not pursued. They are kept as the evidence behind that choice.

The earlier prototype used **CPython 3.12 compiled to WASI**, release `python/3.12.0+20231211-040d5a6` of `vmware-labs/webassembly-language-runtimes`, file `python-3.12.0.wasm` with sha256 `e5dc5a398b07b54ea8fdb503bf68fb583d533f10ec3f930963e02b9505f7a763`, run through a **pure-JavaScript WASI host with an in-memory, read-only filesystem**, inside a worker that can be terminated.

This historical artifact is not a selected production runtime. The [vendor repository](https://github.com/vmware-labs/webassembly-language-runtimes) announces a handoff to a community fork, and its listed Python binary is the older 3.12.0 release. Before choosing a build, review its maintenance, security patch provenance, license, host capabilities, resource enforcement and Vercel compatibility. [WASI isolation](https://wasi.dev/security) depends on the capabilities granted by the host; a prototype alone does not establish a production security boundary.

Measured in a prototype on 2026-10-13:

- Startup about 70 ms.
- Host files unreachable (only the in-memory filesystem exists).
- Sockets unsupported.
- A memory bomb raised `MemoryError` once a memory maximum was patched into the module.
- An infinite loop was killed by terminating the worker.
- About 7-10x slower than native CPython: a 10^7-iteration loop took 5 s, so the current 2 s per-case budget suits small inputs only.

The earlier alternative descriptions were too broad. [Pyodide's `jsglobals`](https://pyodide.org/en/stable/usage/api/js-api.html#pyodideconfig-jsglobals) defaults to `globalThis` but is configurable. A managed judge pilot should explicitly use `networkPolicy: "deny-all"`, no exposed ports, credentials or account-data mounts, and `persistent: false`; [network access is allowed by default](https://vercel.com/docs/sandbox/concepts/firewall). Avoid reusing an execution environment across accounts or hidden cases. The [SDK](https://vercel.com/docs/sandbox/sdk-reference) allocates 2,048 MB per vCPU, which does not enforce this app's 256 MiB per-case limit. A VM timeout also does not prove the 2-second case deadline or 20-second whole-run budget. Enforce and verify those limits, bounded stdout/stderr while streaming, cancellation and teardown of descendants, and hidden-case confidentiality. Do not send a whole hidden suite into an environment after learner code has run there.

The saved `scripts/inspect-python-sandbox.ts` inspection and `scripts/probe-python-sandbox-enforcement.ts` enforcement probe are **manual, trusted-code tools only**. Importing them does not create a VM; neither is wired to application execution. The enforcement probe sends only the checked-in `python-sandbox-enforcement-probe.py` fixture to one 30-second, one-vCPU, deny-all, nonpersistent VM, with a 10-second command deadline, bounded host output streams and a `stop()` in `finally`. It attempts to verify writable cgroup memory/swap, CPU and process controls, a memory OOM kill, CPU throttling, the PID cap, and `cgroup.kill` of a trusted descendant. Its fixed-address outbound connection attempt records only whether the connection succeeded; a failed attempt is inconclusive because routing or the destination could fail independently of the firewall. `networkEnforcementVerified` therefore remains false. Any failed or inconclusive result is a **NO GO** for enabling Python. Local unit tests only verify the caller's configuration, stream cap and cleanup logic; they do not establish VM enforcement.

Even a successful live result would not prove the final learner runner: it does not test a 256 MiB production case limit, two-second case deadline, hidden-case secrecy, per-user/per-case VM isolation, DNS and all network paths, or actual malicious submissions. The next step is a single quota-checked live run of this trusted probe, then a separate bounded runner design and adversarial end-to-end verification before registering an available Python executor or seeding starters. No live VM is started by tests, builds or imports. (Earlier live runs have since happened; see [Earlier live evidence](#earlier-live-evidence-october-20-2026).)

[Hobby quotas](https://vercel.com/docs/sandbox/pricing) currently include 5 active-CPU hours, 420 GB-hours and 5,000 creations per month; exhaustion pauses creation rather than charging overages. Pro usage is metered. AlgoSprint currently admits up to 20 active server executions while Hobby allows 10 concurrent sandboxes, so provider-specific admission/capacity handling is needed. Confirm the actual team plan, remaining quota and budget before a live pilot; no service was activated during this review.

The next approved implementation must preserve the executor contract, reject unsupported execution before reservation, and pass escape/resource/cancellation/cleanup checks in the intended environment. Wire and verify the insert-only starter seed only after that runtime is ready. The existing `test:trace` checks packaging and selected QuickJS behavior; it does not prove Python or a remote judge secure.

## Vercel Sandbox executor

`src/features/submissions/python-vercel-sandbox.ts` contains the managed executor. `getPythonExecutor()` selects it only when all three exact settings above are present; controlled test injection takes precedence in tests.

- **One new VM per test case.** Image pinned to `vercel/sandbox/python@sha256:5db625121b2172bb6af2c08d9d0df094eb7229e5e284a3f4dee673f6408968aa`, one vCPU, `networkPolicy: "deny-all"`, no ports, nothing mounted, no credentials or environment passed in, `persistent: false`, 30 s provider TTL as a backstop. In `finally`, command kill and VM stop are attempted in parallel with separate two-second bounds, so a hung kill cannot prevent stop. Nothing is reused across cases or users, and expected outputs never enter a VM.
- **Files, not arguments.** The generated program and the case input are written under the absolute directory `/vercel/sandbox` (`boot.py`, `program.py`, `input.json`), which is also the working directory. Learner text never appears on a command line.
- **Limits and privilege drop before learner execution.** The image's default user is not a boundary (see the historical live evidence), so the command is started with `sudo` and the trusted bootstrap (`PYTHON_BOOTSTRAP`, `python3 -I -X utf8 /vercel/sandbox/boot.py <cpu seconds> <memory bytes>`) runs as root. While privileged it reads `program.py` and `input.json`, sets `RLIMIT_NPROC` = 1, equal soft/hard CPU containment limits of `ceil(requested seconds) + 1`, data segment and address space to exactly the requested memory bytes, 32 open files, 1 MiB per written file and no core files. There is no memory headroom: the interpreter and learner share that address-space budget. It sets and reads back `no_new_privs`, clears the **inheritable** capability set with `capset` (`setuid` leaves it set) and the **bounding** set, then calls `setgroups([])`, `setgid(65534)`, `setuid(65534)`. Before learner execution, `setuid(0)` must raise `PermissionError`; real, effective and saved uid/gid must all be 65534; no supplementary groups; `no_new_privs` must still read back as 1; `CapInh`, `CapPrm`, `CapEff`, `CapBnd` and `CapAmb` must all be zero. The program is then compiled and run in the same interpreter. `capget`/`capset` syscall numbers are selected by architecture (x86_64 125/126, aarch64 90/91); any other architecture refuses to run. The final integrated bootstrap passed the committed hosted boundary matrix.
- **Setup failure is infrastructure, not the learner.** Any failed step writes `AS_SANDBOX_SETUP_FAILED <reason>` to stderr and exits 70. The host maps exit 70 with that marker to the generic unavailable result. Because stderr is learner-controlled, a learner can forge that marker, but the only effect is an unavailable result for their own run.
- **Fail-closed single-process filter.** Before dropping privileges, the bootstrap installs an additional seccomp BPF filter that denies native process/thread creation (`clone`, `clone3`, and the architecture's `fork`/`vfork` syscalls) and namespace changes (`unshare`, `setns`) with `EPERM`. It checks the syscall audit architecture first, killing a mismatched ABI, and rejects x32 syscall numbers so compatibility paths cannot bypass native syscall numbers. Installation must succeed, seccomp must read back as filter mode, and `/proc/self/status` must show an increased filter count both before and after the identity drop; otherwise setup refuses before learner execution. The filter persists across `exec` and supplements `RLIMIT_NPROC`; the single-process boundary does not rely on per-user process accounting alone. The final integrated filter passed native and compatibility-path hosted checks and independent review.
- **One hard deadline.** `executePython` creates a single `AbortSignal.timeout(totalBudgetMs)` (20 s, monotonic) and passes it to every case; it covers waiting for a slot, VM start-up, upload and the run, and `executePython` also stops waiting on its own. Each case also has its own wall-clock deadline (twice the requested CPU time plus 600 ms). Running out of the **run** budget means the platform was slow, so it is reported as unavailable ("did not finish within the time budget"), never as a time limit on the learner's code.
- **Bounded output on the host.** The command runs detached and without `stdout`/`stderr` options, because @vercel/sandbox 3.8.0 accumulates all output in memory when they are given. Output is read from `Command.logs()` into a collector that keeps at most 256 KiB + 1 byte per stream and kills the command when either stream passes that. A failed log stream or failure to drain within 1.5 seconds after exit is an infrastructure failure; partial output is never judged.
- **Harness behaviour that matches JavaScript.** The harness raises Python's recursion limit to 15,000 (the default 1,000 is far below the roughly 11,000 frames a JavaScript solution gets, and `grove-harvest` has a depth-5,000 tree); an infinite recursion still ends as an ordinary `RecursionError` runtime error in the local harness tests and earlier live variant. `mapPythonRun` compares `-0.0` as `0`, as JavaScript's `JSON.stringify` would write it. Tracebacks start at the first frame in the learner's own code, without the harness's frames.
- **Storable output.** Learner output is stored in a jsonb column, so NUL characters are removed and lone surrogates (including ones created by truncation) are repaired before it leaves `mapPythonRun`.
- **Verdicts:** a trusted root supervisor reaps the learner with `wait4` and writes CPU, signal and peak-RSS accounting to a protected root-only file. CPU above the requested budget is `TIME_LIMIT`, even after a normal return; the equal soft/hard kernel limit provides whole-second containment grace. A case deadline or CPU signal is also `TIME_LIMIT`. Exit 1 with `MemoryError` is `MEMORY_LIMIT`; an unexplained low-CPU SIGKILL is infrastructure failure rather than guessed memory exhaustion. Normal exit 137 remains a runtime error. Exit 3 is a compile error; other non-zero exits are runtime errors. Missing or inconsistent accounting fails closed. Quota, capacity, provider, run-budget and sandbox-setup failures become one generic `INTERNAL_ERROR` message, never a wrong answer. After the first such failure `executePython` stops starting further VMs for that run. The executor logs the error type and numeric status or code (never provider text) with `console.error`.
- **VM budgets** (`src/features/submissions/python-budget.ts`, checked inside the reservation transaction). Python costs one VM per case, up to 10 per Submit, so the submission-count limits (5/min, 30/hour per user, which also cover JavaScript) are far too loose. Python additionally has: at most `PYTHON_MAX_ACTIVE` attempts in flight (default 2, the provider's 10 concurrent sandboxes divided by the run width of 5), `PYTHON_USER_VMS_PER_DAY` per user (default 60) and `PYTHON_VMS_PER_DAY` across all users (default 150), counted from stored `totalCount` over 24 hours, failed and aborted runs included. The defaults suit the Hobby plan (5,000 creations a month is about 166 a day); raise them with those variables on a larger plan. When a budget is exhausted the learner sees a message that names Python only and JavaScript is unaffected.
- **Measured usage:** completed learner processes report trusted `wait4` CPU time, rounded up to integer milliseconds, and peak RSS in KB. The nominal verdict CPU budget is separate from the whole-second kernel containment guard; a nominal 2-second case has a 3-second guard and cannot receive Accepted above 2 seconds of measured CPU.

### What this does and does not guarantee

- **The intended learner process is unprivileged:** uid 65534, no capabilities, `no_new_privs` and limits it cannot raise. The final hosted matrix verified the integrated bootstrap, pinned-image selection and exact memory limit together.
- **No dedicated aggregate cgroup bound.** Per-process resource limits bound the whole program only if process and thread creation are reliably denied after the privilege drop. The added seccomp filter is the intended kernel boundary for that condition; its integrated live evidence was reviewed, including native and compatibility syscall paths. The earlier default-user design failed process denial. The VM provides the outer aggregate bound. `RLIMIT_FSIZE` is per file.
- **Blast radius.** The VM is the outer boundary: one vCPU, 2 GiB, no network, no secrets, 30 s provider TTL, host-side wall-clock kill and `stop()`.
- **Hidden-case information.** Hidden inputs do enter the VM, and Submit reports a pass count and the slowest runtime, so a determined learner can extract a bit per case by passing or failing, or by sleeping. This is the usual judge trade-off and is bounded by the attempt and VM budgets above; it does not reveal expected outputs, which never enter a VM.
- **Programs that use threads or subprocesses are intended to fail** (`can't start new thread`, `BlockingIOError`). The integrated tree passed hosted native and compatibility-path process/thread denial checks. The problem library does not need either.
- **Capacity.** The per-instance gate (8 VMs) and per-run width (5) only keep one server from queueing itself. Concurrency across serverless instances is bounded by the Python active-attempt budget and the provider's quota.
- **Release verification completed:** the final hosted matrix passed, followed by real signed-in production Run/Submit, persistence and JavaScript regression checks. See [production evidence](evidence/python-production-2026-10-21.md).

## Earlier live evidence (October 20, 2026)

The following is the reported evidence from earlier runtime branches against the real image (`vercel/sandbox/python:3.14`: Python 3.14.4, x86_64, kernel 6.18) with a development OIDC token. Dozens of VMs were created in total; `vercel sandbox list` reportedly showed none left afterwards. These runs predate the integrated pinned image, exact address-space limit and final bootstrap readbacks. They do not establish that the integrated tree is ready to activate.

**1. The first design was wrong.** A diagnostic showed the default user (uid/gid 1000, `vercel-sandbox`) holds **all** capabilities (`CapEff`, `CapPrm`, `CapAmb`, `CapBnd` = `0x1ffffffffff`) and has passwordless `sudo` (`sudo -n true` exits 0). `RLIMIT_NPROC` therefore did not stop `fork()` (the process is exempt through `CAP_SYS_RESOURCE`), and any rlimit could be raised again. The earlier text of this document ("runs as the unprivileged user (no `sudo`)", "hard limits cannot be raised") was false for the real image. Other findings: a seccomp filter is already present (mode 2, 1 filter), cgroup v2 is read-only to that user (`memory.max` = 2147483648, `pids.max` = max), 1 vCPU, about 2.2 GB RAM, `/vercel/sandbox` is writable and is the working directory, only 15 benign environment variable names exist (CA bundle paths, `HOME`, `LANG`, `PATH`, `SHELL`, and `SUDO_*` set by sudo), and a TCP connect to 1.1.1.1:53 timed out (one destination only).

**2. The first redesign failed closed on every real run.** The root-then-drop bootstrap passed in a local container but refused all 13 real runs with `AS_SANDBOX_SETUP_FAILED CapInh: 000001ffffffffff`: `setuid` clears the permitted, effective and ambient sets but not the inheritable one. The proof of the drop caught it, so no learner code ran as root, but every submission would have reported "temporarily unavailable". The local container had not shown this. The fix is the `capset` call and bounding-set drop described above.

## Final integration checkpoint (October 20, 2026)

The first integrated probe before the added seccomp filter failed a combined assertion involving `unshare` and process creation. That result was not isolated enough to prove a namespace or process-limit bypass; it remains a failed acceptance check, not evidence of an established exploit. The bootstrap was subsequently hardened with the explicit process/thread/namespace filter and architecture guards above.
