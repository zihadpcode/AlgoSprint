# Local content reconciliation rehearsal

This is a local-only candidate. `scripts/lib/reconcile-content.ts` rejects databases whose actual name does not end in `_test`, exposes no command-line entry point, and reads no deployment credentials. Production backup, baseline capture, execution, and publication require a separately reviewed operator workflow.

The immutable old source is `1bacb2f947de89e92cb4fc08604132c1b78090e0`. The corrected source is `03c3ac9936a4b5ada88a53888d5bb09475f38cca`, incorporating the unchanged `686cfd868601ea7790c8f8bf2a081209eacbc5b7` content checkpoint plus the four approved complexity clarifications. Git objects for both source revisions must be available locally. The 24 changed slugs affect hints and solutions only; Parcel Checkpoints has no constraint cap change.

`captureContentBaseline` validates the complete old source and seed hashes, records all public content rows and their existing identifiers, and captures one UTC database timestamp for the planned reconciliation job. Extra starter languages require an explicit per-slug allowlist and their complete rows are preserved in the baseline. User source, notes, answers, and reports are excluded from the exported baseline.

`reconcileContent` revalidates the immutable source identity and baseline. Inside a repeatable-read transaction it acquires advisory locks `713013` then `712012`, locks all 24 Problem UUIDs deterministically and their existing child rows, and checks every target before changing any. Each target must exactly match the recorded old state or the complete resulting state, including the recorded job timestamp, new hash and revision increment. Recognized mixed states are supported; all other drift aborts the transaction.

Only changed existing hint, solution and solution-step fields are updated by primary key and complete expected old row. Problem updates change only revision, seedHash and updatedAt. No content rows are inserted or deleted. All public content is compared again before commit; private tables are compared using server-side SHA-256 digests so their payloads do not leave PostgreSQL. Unexpected triggers or rewrite rules on mutation tables abort. Budgets are 500 ms for locks, 5 seconds per statement/idle transaction and 25 seconds per PostgreSQL transaction.

The planned updatedAt timestamp is captured before execution, rather than being an unknown post-hoc receipt, so the same reviewed baseline recognizes an exact repeat without changing any timestamp. Capture a fresh baseline immediately before the separately reviewed operation; keep it for idempotent retries. A new capture intentionally rejects an already corrected collection because it requires the pinned old state.

Both capture and execution compare the planned timestamp with target creation/update times and the current database clock using PostgreSQL's full microsecond precision. Mutating the baseline cannot move content dates backward or into the future. The rehearsal's relation fixture is frozen separately from application seeds: its reviewed 1bac source contains exactly 18 roadmaps, 307 steps and 35 videos, with a SHA-256 identity check and typed schema/reference validation. Later content expansions do not alter this fixture. CI fetches only the two pinned source commit objects at depth one; publication must retain the corrected source commit as an ancestor.

`tests/integration/content-reconciliation.test.ts` rehearses first application, byte-identical repeat and seed skip; recognized mixed states; hash/content/status/revision/microsecond-timestamp/child-ID drift; rollback after a real fourth-update conflict; and runner-row/admin-advisory lock timeouts. Local fixtures include 100 original problems, 18 roadmaps, 307 roadmap steps, 35 videos, an added Python starter, verified history, stored source/results, notes and an interview snapshot. The helper does not relabel historical verification or rewrite any of those records. The test fixture restoration code is separate from the reconciliation helper and runs only in the disposable test database.
