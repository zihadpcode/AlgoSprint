An API gateway allows each client at most limit accepted requests in any window-second span. A request from

client at time t is accepted if fewer than limit of that client's previously accepted requests have times

greater than t - window; otherwise it is rejected and not counted. Requests arrive in non-decreasing time order

as [client, time]. Return true or false for each request, in order.

The third request is the third in [1, 3]: rejected. At

11 the request at 1 has aged out (1 <= 11 -

10), so 11 is accepted; at 12, 2 has also aged out.

Clients are

limited independently.

Times only move forward, so a per-client queue can discard expired entries permanently.

Map each client to a queue of accepted times (an array with a head index). Advance the head

past times <= t - window. Reject if the remaining count >= limit; otherwise append t and accept.

This is a sliding-log rate limiter. Each client has a queue of accepted timestamps, expired ones are popped

from the front, and the request is allowed if fewer than limit remain. Amortized O(1). As written the

arrays keep every accepted time, so memory is O(accepted requests); compacting each queue once its head passes

half its length bounds it to O(limit) per active client. In production I'd compare it with a token

bucket or a sliding-window counter, which use O(1) memory per client, and with a shared store like Redis

when several gateway instances enforce the same limit.
