Design a cache with room for capacity entries that evicts the least frequently used key when full. Every

get of a present key and every put counts as a use of that key. When several keys

tie for the lowest use count, evict the one used least recently. Operations arrive as ["put", key, value]

or ["get", key]. A put of an existing key updates its value (and counts as a use). Return

the results of every get in order: the stored value, or -1 if the key is absent.

Key 2 (used once) is evicted for

3. When 4 arrives, keys 1 and

3 both have two uses; 1 was

used less recently, so it is evicted.

A missing key returns -1.

Ordered groups per use count make the victim the first key of the lowest non-empty group, which a

single minimum pointer tracks.

values: key → value; freq: key → count; buckets: count → Set of keys in recency order; minFreq.

touch(key) moves the key to count + 1 and bumps minFreq if its old bucket emptied and was

the minimum. A new key evicts the first key of buckets[minFreq] when full, then enters bucket 1 and

sets minFreq = 1.

I keep a bucket of keys per use count, each an insertion-ordered Set so its first key is

the least recently used at that count, plus a minFreq pointer. A use moves the key up one

bucket and adjusts minFreq

only if it emptied the minimum bucket. A new key always resets minFreq to 1. Everything is O(1).

In languages without ordered sets, each bucket would be a doubly linked list with a map from key

to node. This O(1) bound

relies on the engine’s Set keeping a linked insertion order, as the judge’s QuickJS does; in engines where

repeated deletions leave tombstones that iteration must skip, taking the first key can degrade, and the explicit

linked list is the safe choice.

After the first five operations: buckets {1: [3], 2: [1]}, minFreq 1.

get 3 moves 3 to bucket 2 → {2: [1, 3]}, minFreq 2.

put 4 when full evicts the first of bucket 2 (key 1), then inserts 4 at count 1.
